# RAGAS. Lessons: 1 why evaluate, 2 faithfulness, 3 relevancy/precision/recall, 4 more metrics, 5 data structures, 6 v0.4 API, 7 testset generation, 8 custom metrics/integrations
@ Ragas | 1
D: An open-source library for evaluating LLM applications — originally RAG, now also agents — with metrics, test generation and experiments.
T: Ragas stands for Retrieval Augmented Generation Assessment.
F: Ragas is a vector database.
C: pip install ragas

@ Retrieval vs generation failures | 1
D: RAG can fail because the retriever finds the wrong context or because the generator misuses good context.
T: Context recall diagnoses retrieval, while faithfulness diagnoses generation.
F: All RAG failures come from the LLM, never from retrieval.
C: # low context recall -> fix retrieval; low faithfulness -> fix generation

@ BLEU and ROUGE limitations | 1
D: N-gram overlap metrics that penalize correct paraphrases and can reward fluent wrong answers.
T: A correct paraphrase can get a low ROUGE score.
F: BLEU reliably detects hallucinations.
C: # "Paris is France's capital" vs "The capital of France is Paris"

@ LLM-as-a-judge | 1
D: Using an LLM to score specific, well-defined properties of outputs at scale.
T: Many Ragas metrics use an LLM to extract and verify claims.
F: LLM-as-a-judge metrics never make API calls.
C: llm = llm_factory("gpt-5.4-mini", client=AsyncOpenAI())

@ CI quality gate | 1
D: Failing a build when evaluation scores drop below thresholds such as faithfulness ≥ 0.8.
U: You want to block prompt changes that cause hallucinations from being merged.
T: A small eval set can run on every pull request.
F: Quality gates should only run once a year.
C: assert mean_faithfulness >= 0.8, "faithfulness regression"

@ Faithfulness | 2
D: The fraction of claims in the response that are supported by the retrieved context.
U: You need to measure how often your RAG app hallucinates beyond its sources.
T: Faithfulness = supported claims / total claims in the response.
F: Faithfulness compares the response with the ground-truth reference answer.
C: Faithfulness(llm=llm).ascore(user_input=q, response=a, retrieved_contexts=ctx)

@ Claim extraction | 2
D: Breaking a response or reference into individual factual statements for verification.
T: Faithfulness first splits the response into claims.
F: Claim extraction counts the number of words in the answer.
C: # "Einstein was born in Germany on 20 March 1879" -> 2 claims

@ Faithful but wrong | 2
D: An answer fully supported by retrieved context that is still incorrect because the context was wrong.
T: Faithfulness measures grounding, not real-world truth.
F: A faithfulness score of 1.0 guarantees the answer is factually correct.
C: # wrong context + grounded answer = faithful but incorrect

@ HHEM faithfulness | 2
D: A faithfulness variant using Vectara's hallucination evaluation classifier instead of an LLM judge.
T: HHEM-based scoring can be cheaper than LLM-judged faithfulness.
F: HHEM is an embedding model for retrieval.
C: # FaithfulnesswithHHEM

@ Answer relevancy | 3
D: The mean cosine similarity between the user question and N questions generated from the response.
U: Answers are factually fine but often drift off-topic or are incomplete.
T: Answer relevancy needs an LLM and an embedding model.
F: Answer relevancy measures factual correctness against a reference.
C: AnswerRelevancy(llm=llm, embeddings=emb).ascore(user_input=q, response=a)

@ Generated questions (strictness) | 3
D: The number of questions (default 3) the judge generates from the response for answer relevancy.
T: Answer relevancy averages over several generated questions.
F: Answer relevancy generates exactly one question with no averaging.
C: # strictness / N = 3

@ Context precision | 3
D: Whether relevant retrieved chunks are ranked near the top: Σ(precision@k × v_k) / relevant chunks in top K.
U: Relevant chunks are retrieved but often buried under irrelevant ones.
T: Context precision rewards ranking relevant chunks earlier.
F: Context precision ignores the order of retrieved chunks.
C: ContextPrecision(llm=llm).ascore(user_input=q, reference=ref, retrieved_contexts=ctx)

@ Context recall | 3
D: The fraction of claims in the reference answer that are supported by the retrieved context.
U: Answers miss key facts and you suspect retrieval isn't finding them.
T: Context recall requires a reference answer.
F: Context recall can be computed without any reference.
C: ContextRecall(llm=llm).ascore(user_input=q, retrieved_contexts=ctx, reference=ref)

@ Context precision with reference | 3
D: Context precision where chunk relevance is judged against a reference answer.
T: ContextPrecisionWithReference needs the reference field.
F: ContextPrecisionWithReference ignores the reference.
C: ContextPrecisionWithReference(llm=llm)

@ Context utilization | 3
D: Context precision judged against the response instead of a reference (context precision without reference).
T: Context utilization can run without ground truth.
F: Context utilization requires human labels.
C: ContextUtilization(llm=llm)

@ Metric diagnosis table | 3
D: Mapping low metrics to causes: faithfulness → hallucination, relevancy → drift, precision → noisy ranking, recall → missing info.
T: Low context precision suggests adding a reranker.
F: Low context recall means the generator hallucinates.
C: # recall low -> chunking, k, hybrid search; precision low -> rerank

@ Context entities recall | 4
D: The fraction of entities in the reference that also appear in the retrieved context.
U: Your domain depends on exact entities like drug names and dates.
T: Context entities recall = |entities(context) ∩ entities(reference)| / |entities(reference)|.
F: Context entities recall counts entities in the response only.
C: ContextEntityRecall(llm=llm)

@ Noise sensitivity | 4
D: How often the system makes incorrect claims because of irrelevant retrieved context; lower is better.
T: For noise sensitivity, a lower score is better.
F: For noise sensitivity, higher scores are better.
C: NoiseSensitivity(llm=llm)

@ Factual correctness | 4
D: Claim-level precision, recall or F1 between the response and the reference answer.
T: Factual correctness can be reported as F1.
F: Factual correctness compares the response with the retrieved context only.
C: FactualCorrectness(llm=llm, mode="f1")

@ Semantic similarity | 4
D: Cosine similarity between embeddings of the response and the reference answer.
T: Semantic similarity needs an embedding model but no LLM judge.
F: Semantic similarity uses BLEU n-grams.
C: SemanticSimilarity(embeddings=emb)

@ Answer correctness (legacy) | 4
D: A legacy weighted combination of factual similarity and semantic similarity to the reference.
T: Answer correctness blends factual and semantic similarity.
F: Answer correctness ignores the reference.
C: # weights e.g. [0.75 factual, 0.25 semantic]

@ NVIDIA metrics | 4
D: Ragas metrics such as Answer Accuracy, Context Relevance and Response Groundedness that use LLM-judged ratings.
T: Response groundedness is one of the NVIDIA-style metrics in Ragas.
F: NVIDIA metrics require a GPU to compute.
C: from ragas.metrics.collections import AnswerAccuracy, ContextRelevance, ResponseGroundedness

@ Non-LLM metrics | 4
D: Deterministic metrics like BLEU, ROUGE, chrF, exact match, string presence and string similarity.
T: Non-LLM metrics are cheap and reproducible.
F: Non-LLM metrics require an LLM call per sample.
C: ExactMatch(); RougeScore(); BleuScore()

@ Tool call accuracy | 4
D: Agent metric checking whether the expected tools were called with the expected arguments (and order).
U: You need to verify your agent calls get_weather before book_trip.
T: Tool call accuracy compares actual tool calls with reference_tool_calls.
F: Tool call accuracy measures response fluency.
C: ToolCallAccuracy()

@ Agent goal accuracy | 4
D: Agent metric judging whether the agent achieved the user's goal, with or without a reference.
T: Agent goal accuracy has with-reference and without-reference variants.
F: Agent goal accuracy counts tokens.
C: AgentGoalAccuracyWithReference(llm=llm)

@ Topic adherence | 4
D: Agent metric checking whether the conversation stays within allowed topics.
U: A banking bot must not discuss medical advice.
T: Topic adherence evaluates staying within reference topics.
F: Topic adherence checks code syntax.
C: TopicAdherence(llm=llm)

@ user_input | 5
D: The Ragas field holding the user's question or query.
T: user_input replaced the old field name question.
F: user_input holds the retrieved chunks.
C: SingleTurnSample(user_input="What is the refund window?", ...)

@ retrieved_contexts | 5
D: The Ragas field holding the list of retrieved chunk strings.
T: retrieved_contexts replaced the old field name contexts.
F: retrieved_contexts is a single string, not a list.
C: retrieved_contexts=["Refunds are accepted within 30 days."]

@ response | 5
D: The Ragas field holding the system's generated answer.
T: response replaced the old field name answer.
F: response holds the ground-truth answer.
C: response="You can request a refund within 30 days."

@ reference | 5
D: The Ragas field holding the ground-truth answer.
T: reference replaced the old field name ground_truth.
F: reference holds the model's answer.
C: reference="30 days from delivery."

@ reference_contexts | 5
D: The Ragas field holding the ground-truth relevant contexts for a question.
T: Synthetic test generation produces reference_contexts.
F: reference_contexts are the chunks your retriever returned.
C: reference_contexts=["Refunds are accepted within 30 days of delivery."]

@ Judge alignment | 8

> How Ragas computes faithfulness | 2 | split the response into claims ; check each claim against the retrieved context ; count supported claims ; divide by the total number of claims
> How Ragas computes answer relevancy | 3 | generate N questions from the response ; embed the generated questions and the user input ; compute cosine similarity for each ; average the similarities
> Evaluation workflow with Ragas | 1 | build a representative test set ; choose metrics for each failure mode ; run an experiment for each app version ; inspect failing samples ; add a CI quality gate
