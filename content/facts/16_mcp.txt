# MCP. Lessons: 1 what/why, 2 architecture/lifecycle, 3 JSON-RPC/base protocol, 4 tools, 5 resources/prompts, 6 sampling/roots/elicitation, 7 transports, 8 building servers/clients, 9 security/auth/production
@ Model Context Protocol (MCP) | 1
D: An open protocol that standardises how AI applications connect to external tools, data and prompts.
U: Your company wants one integration for its ticketing system that works in Claude, VS Code and an in-house agent.
T: MCP was open-sourced by Anthropic in November 2024 and is now governed under the Linux Foundation.
F: MCP is a proprietary API that only works with Anthropic models.
C: from mcp.server.fastmcp import FastMCP\nmcp = FastMCP("tickets")

@ M × N integration problem | 1
D: Without a shared standard, every AI app needs a custom connector for every external system.
U: Five AI apps each need to reach eight internal systems and each pair has its own hand-written connector.
T: MCP reduces M × N custom integrations to M + N: each app implements a client once and each system a server once.
F: MCP increases the number of integrations because every app needs a separate server for every model.

@ USB-C for AI applications | 1
D: The common analogy for MCP: one standard plug shape that many tools and apps can share.
T: The USB-C analogy describes MCP as a universal connector between AI apps and capabilities.
F: The USB-C analogy means MCP physically connects GPUs to language models.

@ MCP specification version | 1
D: A date string such as 2025-11-25 that identifies a revision of the protocol.
U: A client and server must agree which protocol revision they will speak during initialization.
T: MCP spec versions are dates in YYYY-MM-DD format, changed only for backwards-incompatible changes.
F: MCP spec versions use semantic versioning like 3.2.1.
C: "protocolVersion": "2025-11-25"

@ Function calling | 1
D: A model feature where tool schemas are passed in an API request and the model returns a structured call for your code to execute.
U: You call a model API directly with a JSON schema for one function and execute the returned call yourself.
T: Hosts usually convert MCP tools into function-calling tool definitions for the model they use.
F: MCP and function calling are competing alternatives, so an app must choose one or the other.

@ Agentic AI Foundation | 1
D: The Linux Foundation body to which MCP was donated in December 2025 for vendor-neutral governance.
T: MCP's governance moved to a Linux Foundation foundation so no single vendor controls the standard.
F: MCP is still owned and governed solely by a single private company.

@ Host | 2
D: The AI application the user interacts with; it owns the LLM, the UI and security decisions and runs one client per server.
U: Claude Desktop, VS Code or your custom agent application that users chat with.
T: The host decides what context each server receives and enforces user consent.
F: The host is the program that exposes tools over MCP.

@ MCP client | 2
D: A connector inside the host that maintains a 1:1 connection with a single MCP server.
U: A host configured with three servers creates this component three times.
T: Each MCP client talks to exactly one server.
F: A single MCP client multiplexes connections to every configured server.
C: async with ClientSession(read, write) as session:\n    await session.initialize()

@ MCP server | 2
D: A program that exposes tools, resources and prompts to MCP clients.
U: You wrap your company's Postgres database so any MCP-compatible app can query it.
T: MCP servers are isolated from each other and cannot see the full conversation.
F: An MCP server can read the messages and tools of other servers connected to the same host.
C: mcp = FastMCP("postgres")\n\n@mcp.tool()\ndef query(sql: str) -> list[dict]: ...

@ Local server | 2
D: An MCP server launched as a subprocess on the user's machine, usually over stdio.
U: A filesystem server that reads files from the user's laptop.
T: Local servers usually get credentials from environment variables rather than OAuth.
F: Local servers must always use OAuth 2.1 over HTTPS.

@ Remote server | 2
D: An MCP server running as a web service that clients reach over Streamable HTTP.
U: A SaaS vendor hosts an MCP endpoint that thousands of users connect to with OAuth.
T: Remote servers typically use Streamable HTTP with OAuth-based authorization.
F: Remote servers can only communicate over stdio.

@ initialize request | 2
D: The first request a client sends, carrying its protocolVersion, capabilities and clientInfo.
U: A client has just connected to a server and nothing else has been exchanged yet.
T: The initialize request must not be part of a batch and comes before any other request except ping.
F: The server sends the initialize request to the client after the first tool call.
C: {"jsonrpc": "2.0", "id": 1, "method": "initialize", "params": {"protocolVersion": "2025-11-25", "capabilities": {}, "clientInfo": {"name": "app", "version": "1.0"}}}
B: {"jsonrpc": "2.0", "id": 1, "method": "____", "params": {"protocolVersion": "2025-11-25"}} ;; initialize ;; connect ;; handshake ;; tools/list

@ notifications/initialized | 2
D: The notification the client sends after a successful initialize response to signal it is ready for normal operation.
T: The client sends notifications/initialized after receiving the server's initialize result.
F: notifications/initialized is a request that the server must answer with a result.
C: {"jsonrpc": "2.0", "method": "notifications/initialized"}

@ Version negotiation | 2
D: The client proposes the latest protocol version it supports and the server replies with that version or another it supports.
U: A client speaks 2025-11-25 but the server only supports 2025-06-18.
T: If the client cannot support the version the server returns, it should disconnect.
F: If versions differ, both sides silently switch to the oldest version ever published.

@ Capability negotiation | 2
D: The exchange during initialization where client and server declare which optional features they support.
U: A server wants to know whether it may send sampling requests to the client.
T: Only features negotiated during initialization may be used in the session.
F: Capabilities are discovered by trial and error after initialization.
C: "capabilities": {"tools": {"listChanged": true}, "resources": {"subscribe": true}}

@ listChanged | 2
D: A capability flag meaning the sender will notify the other side when its list of tools, resources, prompts or roots changes.
T: A server declaring tools.listChanged will send notifications/tools/list_changed when its tools change.
F: listChanged means the client must poll tools/list every second.
C: "tools": {"listChanged": true}

@ serverInfo | 2
D: The name and version of the server implementation returned in the initialize result.
T: The initialize result contains protocolVersion, capabilities, serverInfo and optional instructions.
F: serverInfo is sent by the client to describe the host application.

@ instructions | 2
D: Optional text in the initialize result that tells the host or model how to use the server.
T: Servers can include an instructions string in the initialize result to guide models.
F: instructions is a required field that lists every tool's source code.

@ Shutdown | 2
D: Ending an MCP connection, done through the transport: closing stdin for stdio or closing connections and sending DELETE for HTTP.
T: MCP defines no special shutdown message; the transport is used to end the connection.
F: Shutdown requires a JSON-RPC request named shutdown that the server must answer.

@ JSON-RPC 2.0 | 3
D: The lightweight remote-procedure-call message format that all MCP messages use.
T: Every MCP message includes "jsonrpc": "2.0".
F: MCP messages are encoded in Protocol Buffers.
C: {"jsonrpc": "2.0", "id": 7, "method": "tools/call", "params": {"name": "add"}}

@ Request | 3
D: A JSON-RPC message with an id and a method that expects a response.
U: The client asks the server to run a tool and waits for the result.
T: MCP request ids must be strings or integers and never null.
F: MCP request ids may be null as long as the method is unique.
C: {"jsonrpc": "2.0", "id": 2, "method": "tools/list"}

@ Response | 3
D: A JSON-RPC message that carries the same id as a request and either a result or an error.
T: A response contains either result or error, never both.
F: A response can contain both a result and an error at the same time.
C: {"jsonrpc": "2.0", "id": 2, "result": {"tools": []}}

@ Notification | 3
D: A one-way JSON-RPC message with a method but no id, which gets no reply.
U: The server tells the client its tool list changed and does not need an answer.
T: Notifications have no id field and must not be answered.
F: Every notification must be acknowledged with a response.
C: {"jsonrpc": "2.0", "method": "notifications/tools/list_changed"}

@ JSON-RPC batching | 3
D: Sending several JSON-RPC messages as one array, which MCP removed in the 2025-06-18 revision.
T: Since 2025-06-18, MCP does not support JSON-RPC batch arrays.
F: MCP requires all requests to be sent in batch arrays.

@ Method not found (-32601) | 3
D: The JSON-RPC error returned when the method does not exist or its capability was not negotiated.
U: A client calls prompts/list on a server that never declared the prompts capability.
T: Calling an unsupported method returns error code -32601.
F: -32601 means the JSON could not be parsed.
C: {"jsonrpc": "2.0", "id": 5, "error": {"code": -32601, "message": "Method not found"}}

@ Invalid params (-32602) | 3
D: The JSON-RPC error for bad arguments, such as an unknown tool name or missing required parameter.
U: The client calls tools/call with a tool name the server does not have.
T: An unknown tool name in tools/call is reported as a protocol error with code -32602.
F: -32602 is used when the server crashes unexpectedly.
C: {"jsonrpc": "2.0", "id": 9, "error": {"code": -32602, "message": "Unknown tool: foo"}}

@ Parse error (-32700) | 3
D: The JSON-RPC error returned when the received text is not valid JSON.
T: Invalid JSON produces error code -32700.
F: -32700 means a requested resource was not found.

@ Resource not found (-32002) | 3
D: The MCP-specific error code returned when resources/read is asked for a URI that does not exist.
T: MCP uses error code -32002 for a missing resource.
F: A missing resource is reported with HTTP status 418.
C: {"jsonrpc": "2.0", "id": 5, "error": {"code": -32002, "message": "Resource not found", "data": {"uri": "file:///nope"}}}

@ ping | 3
D: A request either side can send to check that the connection is alive; the receiver replies with an empty result.
U: A client wants to detect a dead server before sending a long request.
T: Either the client or the server may send ping.
F: ping is a notification, so it never gets a reply.
C: {"jsonrpc": "2.0", "id": "p1", "method": "ping"}

@ Progress notifications | 3
D: notifications/progress messages sent for a long request, identified by the progressToken the requester placed in params._meta.
U: A tool processes 500 files and the host wants to show a progress bar.
T: Progress is only sent if the requester included a progressToken in the request's _meta.
F: Servers must send progress notifications for every request even without a progressToken.
C: {"jsonrpc": "2.0", "method": "notifications/progress", "params": {"progressToken": "abc", "progress": 50, "total": 100}}

@ Cancellation | 3
D: notifications/cancelled, sent with the requestId of an in-flight request the sender no longer needs.
U: The user clicks Stop while a slow tool call is still running.
T: A cancelled request is identified by its requestId in notifications/cancelled.
F: Cancellation is done by sending the same request again with a negative id.
C: {"jsonrpc": "2.0", "method": "notifications/cancelled", "params": {"requestId": 7, "reason": "User pressed stop"}}

@ Pagination | 3
D: Splitting list results into pages: the result includes nextCursor, which the client sends back as cursor.
U: A server has 2,000 resources and the client must fetch all of them.
T: A missing nextCursor in a list result means there are no more pages.
F: Clients must compute page numbers themselves and send page=2, page=3 and so on.
C: {"jsonrpc": "2.0", "id": 3, "method": "resources/list", "params": {"cursor": "eyJwYWdlIjogMn0="}}

@ Logging | 3
D: The utility where servers send notifications/message log entries and clients set the minimum level with logging/setLevel.
T: MCP log levels follow syslog severities such as debug, info, warning and error.
F: MCP logging requires servers to write logs to stdout on the stdio transport.
C: {"jsonrpc": "2.0", "method": "notifications/message", "params": {"level": "warning", "data": "Rate limit close"}}

@ completion/complete | 3
D: The request that asks a server to suggest values for a prompt argument or resource-template variable.
U: The user types "/review lang=py" and the host wants to autocomplete the argument.
T: Servers declare the completions capability to support argument autocompletion.
F: completion/complete runs a full LLM chat completion on the server.

@ _meta | 3
D: A reserved field on many MCP objects for extra metadata such as progress tokens.
T: The progressToken is placed in the params._meta object of a request.
F: _meta fields are always shown to the model as part of the prompt.

@ Tool | 4
D: A function a server exposes for the model to call, described by a name, description and JSON Schema for its input.
U: You want the model to be able to create GitHub issues on the user's behalf.
T: Tools are model-controlled: the LLM decides when to call them, with the user able to approve.
F: Tools are user-controlled templates that appear only as slash commands.
C: @mcp.tool()\ndef create_issue(repo: str, title: str) -> str:\n    """Create a GitHub issue."""

@ tools/list | 4
D: The request a client sends to discover the tools a server offers.
T: tools/list results can be paginated with nextCursor.
F: tools/list executes every tool once to test it.
C: {"jsonrpc": "2.0", "id": 2, "method": "tools/list"}
B: {"jsonrpc": "2.0", "id": 2, "method": "____"} ;; tools/list ;; tools/get ;; list_tools ;; tools/discover

@ tools/call | 4
D: The request a client sends to invoke a tool with a name and arguments.
U: The model decided to call get_weather with city "Pune" and the host forwards it to the server.
T: tools/call params contain the tool name and an arguments object.
F: tools/call is a notification, so the client never receives the tool's result.
C: {"jsonrpc": "2.0", "id": 7, "method": "tools/call", "params": {"name": "get_weather", "arguments": {"city": "Pune"}}}
B: {"method": "tools/call", "params": {"name": "get_weather", "____": {"city": "Pune"}}} ;; arguments ;; input ;; args_json ;; parameters

@ inputSchema | 4
D: The JSON Schema object that describes a tool's arguments.
T: A tool's inputSchema must be a JSON Schema whose type is object.
F: inputSchema is optional free text describing the arguments in prose.
C: "inputSchema": {"type": "object", "properties": {"city": {"type": "string"}}, "required": ["city"]}
B: "inputSchema": {"type": "____", "properties": {"city": {"type": "string"}}} ;; object ;; dict ;; record ;; array

@ outputSchema | 4
D: An optional JSON Schema describing the structuredContent a tool returns.
U: Your agent code needs typed, machine-readable tool results it can validate.
T: If a tool declares an outputSchema, its results must include structuredContent that conforms to it.
F: outputSchema replaces inputSchema, so tools with an output schema take no arguments.
C: "outputSchema": {"type": "object", "properties": {"temp_c": {"type": "number"}}, "required": ["temp_c"]}

@ structuredContent | 4
D: A JSON object in a tool result holding machine-readable output, alongside the content array.
T: For backwards compatibility, tools returning structuredContent should also include the serialized JSON in a text content block.
F: structuredContent can only contain base64-encoded images.
C: {"content": [{"type": "text", "text": "{\"temp_c\": 21}"}], "structuredContent": {"temp_c": 21}}

@ isError | 4
D: A flag in a tool result marking a tool execution failure, so the model can see the error and retry.
U: A tool's upstream API rejects a date in the past and you want the model to fix its input.
T: Tool execution errors are returned as results with isError true rather than as JSON-RPC errors.
F: Any failure inside a tool must be reported as a JSON-RPC error so the model never sees it.
C: {"content": [{"type": "text", "text": "Date must be in the future"}], "isError": true}
B: {"content": [{"type": "text", "text": "API rate limited, retry in 30s"}], "____": true} ;; isError ;; error ;; failed ;; exception

@ Content block | 4
D: An item in a tool result's content array, such as text, image, audio, resource_link or an embedded resource.
T: Image and audio content blocks carry base64 data plus a mimeType.
F: Tool results may only contain a single plain-text string.
C: {"type": "image", "data": "iVBORw0KGgo...", "mimeType": "image/png"}

@ resource_link | 4
D: A content block in a tool result that points to a resource by URI instead of embedding its contents.
U: A search tool returns ten matching files without sending their full text.
T: A resource_link lets the client read the resource later with resources/read.
F: A resource_link always embeds the full file contents inline.
C: {"type": "resource_link", "uri": "file:///repo/src/app.py", "name": "app.py", "mimeType": "text/x-python"}

@ Tool annotations | 4
D: Optional hints such as readOnlyHint, destructiveHint, idempotentHint and openWorldHint describing a tool's behaviour.
U: The host wants to auto-approve harmless lookups but ask before anything destructive.
T: Clients must treat tool annotations as untrusted unless they come from a trusted server.
F: Tool annotations are enforced guarantees that the server cannot violate.
C: "annotations": {"readOnlyHint": true, "openWorldHint": false}

@ readOnlyHint | 4
D: A tool annotation meaning the tool does not modify its environment; it defaults to false.
T: readOnlyHint defaults to false when it is not specified.
F: readOnlyHint defaults to true, so tools are assumed safe unless marked otherwise.
C: "annotations": {"readOnlyHint": true}

@ destructiveHint | 4
D: A tool annotation meaning the tool may perform destructive updates; it defaults to true and only matters when the tool is not read-only.
T: destructiveHint defaults to true for tools that are not read-only.
F: destructiveHint defaults to false, so deleting tools must opt in to be treated as risky.
C: "annotations": {"readOnlyHint": false, "destructiveHint": true}

@ idempotentHint | 4
D: A tool annotation meaning repeated calls with the same arguments have no additional effect; it defaults to false.
U: A "set_status" tool can safely be retried after a network timeout.
T: idempotentHint defaults to false.
F: idempotentHint means the tool returns a different random result on each call.

@ openWorldHint | 4
D: A tool annotation meaning the tool interacts with an open world of external entities such as the web; it defaults to true.
U: A web search tool whose results come from the public internet.
T: openWorldHint defaults to true.
F: openWorldHint means the tool's source code is open source.

@ notifications/tools/list_changed | 4
D: The notification a server sends when its set of available tools changes.
T: After notifications/tools/list_changed, the client should call tools/list again.
F: notifications/tools/list_changed contains the full source code of every tool.
C: {"jsonrpc": "2.0", "method": "notifications/tools/list_changed"}

@ Tool description | 4
D: Natural-language text explaining what a tool does and when to use it, which the model reads to choose tools.
U: The model keeps calling search_orders when it should call search_customers.
T: Clear, distinct tool descriptions improve the model's tool selection.
F: Tool descriptions are never shown to the model, only to the user.

@ Resource | 5
D: A piece of data identified by a URI, such as a file, schema or record, that a server exposes for reading as context.
U: The host lets the user @-mention a database schema so the model can see it.
T: Resources are application-controlled: the host decides what to read and attach as context.
F: Resources are functions the model calls to change external systems.
C: @mcp.resource("schema://main")\ndef schema() -> str:\n    return get_schema_sql()

@ resources/read | 5
D: The request a client sends to fetch the contents of a resource by URI.
T: resources/read returns a contents array whose items have either text or a base64 blob.
F: resources/read deletes the resource after reading it.
C: {"jsonrpc": "2.0", "id": 3, "method": "resources/read", "params": {"uri": "file:///project/README.md"}}
B: {"jsonrpc": "2.0", "id": 3, "method": "resources/read", "params": {"____": "file:///README.md"}} ;; uri ;; path ;; url_path ;; resource_id

@ resources/list | 5
D: The request a client sends to list a server's concrete resources, with pagination.
T: resources/list returns resources with fields such as uri, name, mimeType and description.
F: resources/list returns the full contents of every resource.

@ Resource template | 5
D: A parameterised resource definition using an RFC 6570 URI template such as weather://forecast/{city}.
U: You want one definition to cover a forecast resource for every possible city.
T: Resource templates are discovered with resources/templates/list.
F: Resource templates must be listed one URI at a time with resources/list.
C: @mcp.resource("weather://forecast/{city}")\ndef forecast(city: str) -> str: ...

@ blob | 5
D: The base64-encoded field used for binary resource contents such as images or PDFs.
T: Binary resource contents are returned as base64 in a blob field.
F: Binary files must be returned as raw bytes inside the text field.
C: {"uri": "file:///logo.png", "mimeType": "image/png", "blob": "iVBORw0KGgo..."}

@ Resource subscription | 5
D: A client asking with resources/subscribe to be told via notifications/resources/updated when a resource changes.
U: The host shows a live log file and wants to refresh it when new lines arrive.
T: Servers declare resources.subscribe to support subscriptions.
F: Subscriptions push the new contents automatically, so resources/read is never needed again.
C: {"jsonrpc": "2.0", "id": 8, "method": "resources/subscribe", "params": {"uri": "file:///var/log/app.log"}}

@ Resource annotations | 5
D: Optional hints on resources: audience (user or assistant), priority from 0 to 1, and lastModified.
T: A resource priority of 1.0 means the resource is effectively required.
F: Resource priority is an integer from 1 to 100 chosen by the user.
C: "annotations": {"audience": ["assistant"], "priority": 0.9, "lastModified": "2026-11-01T10:00:00Z"}

@ Prompt | 5
D: A reusable, parameterised message template a server exposes for the user to choose, often shown as a slash command.
U: You want users to type /review-pr and get a well-structured code-review request.
T: Prompts are user-controlled: the user explicitly selects them.
F: Prompts are selected automatically by the model without the user's involvement.
C: @mcp.prompt()\ndef review_pr(diff: str) -> str:\n    return f"Review this diff: {diff}"

@ prompts/get | 5
D: The request that fetches a prompt by name with arguments and returns a list of role-tagged messages.
T: prompts/get returns messages whose role is user or assistant.
F: prompts/get returns a single string with no roles.
C: {"jsonrpc": "2.0", "id": 4, "method": "prompts/get", "params": {"name": "code_review", "arguments": {"language": "python"}}}
B: {"method": "prompts/get", "params": {"____": "code_review", "arguments": {"language": "python"}}} ;; name ;; id ;; prompt_id ;; template

@ Sampling | 6
D: A client feature where a server asks the host's LLM to generate a completion via sampling/createMessage.
U: Your server wants to summarise a diff with an LLM but should not hold its own API key.
T: With sampling, the host keeps control over which model runs and can let the user review the request.
F: Sampling requires the server to ship its own model weights.
C: {"method": "sampling/createMessage", "params": {"messages": [{"role": "user", "content": {"type": "text", "text": "Summarise"}}], "maxTokens": 100}}
B: {"method": "sampling/____", "params": {"messages": [], "maxTokens": 100}} ;; createMessage ;; complete ;; generate ;; chat

@ Model preferences | 6
D: Advisory sampling hints: model-name hints plus costPriority, speedPriority and intelligencePriority values from 0 to 1.
U: A server prefers a fast, cheap model for a simple classification step.
T: The client makes the final model choice; model preferences are only advisory.
F: Model preferences force the client to use the exact model named in the hints.
C: "modelPreferences": {"hints": [{"name": "claude-sonnet"}], "costPriority": 0.3, "speedPriority": 0.8}

@ Roots | 6
D: URIs, usually file:// folders, that a client exposes to tell a server which parts of the filesystem are in scope.
U: The user opens a different project folder and the filesystem server should work there instead.
T: Clients send notifications/roots/list_changed when the set of roots changes.
F: Roots are a security sandbox that makes it impossible for a server to access other paths.
C: {"roots": [{"uri": "file:///home/sam/projects/shop", "name": "shop"}]}

@ Elicitation | 6
D: A client feature where a server asks the user for extra structured input through the host via elicitation/create.
U: A deploy tool needs the user to choose staging or production before continuing.
T: Elicitation was added to MCP in the 2025-06-18 revision.
F: Elicitation lets the model answer the server's questions without involving the user.
C: {"method": "elicitation/create", "params": {"message": "Which environment?", "requestedSchema": {"type": "object", "properties": {"env": {"type": "string", "enum": ["staging", "production"]}}}}}

@ requestedSchema | 6
D: The restricted JSON Schema in a form-mode elicitation: a flat object whose properties are primitive types.
T: Elicitation schemas only allow flat objects with string, number, integer, boolean or enum properties.
F: Elicitation schemas may contain deeply nested objects and arrays of objects.

@ Elicitation response actions | 6
D: The three outcomes of an elicitation request: accept with data, decline, or cancel.
U: The user closes the dialog without choosing anything.
T: decline means the user explicitly refused, while cancel means they dismissed without choosing.
F: The only possible elicitation response is accept.
C: {"action": "accept", "content": {"env": "staging"}}

@ URL-mode elicitation | 6
D: Elicitation that sends the user to an external URL, so sensitive data such as credentials or payments never passes through the client.
U: A server needs the user to sign in to a third-party service and authorise access.
T: URL-mode elicitation was added in the 2025-11-25 revision for sensitive interactions.
F: Form-mode elicitation is the recommended way to collect passwords and API keys.

@ Tasks (experimental) | 6
D: An experimental 2025-11-25 feature that turns a long-running request into a task with an id that can be polled for status and results later.
U: A tool starts a data export that takes twenty minutes.
T: Tasks follow a "call now, fetch later" pattern.
F: Tasks are a stable feature from the very first 2024-11-05 specification.

@ stdio transport | 7
D: The transport where the client launches the server as a subprocess and exchanges newline-delimited JSON-RPC messages over stdin and stdout.
U: A local git server runs on the user's laptop with no network exposure.
T: On stdio, the server must not write anything to stdout that is not a valid MCP message.
F: On stdio, servers should print debug logs to stdout so the client can display them.
C: StdioServerParameters(command="python", args=["server.py"])

@ stderr logging | 7
D: Writing diagnostic logs to standard error so stdout stays reserved for protocol messages.
U: Your stdio server needs to print "starting up" without corrupting the protocol stream.
T: stdio servers may write UTF-8 logs to stderr.
F: Clients must treat any text on stderr as a fatal protocol error.
C: print("server started", file=sys.stderr)
B: import sys\nprint("starting", file=sys.____) ;; stderr ;; stdout ;; stdin ;; log

@ Streamable HTTP | 7
D: The remote transport introduced in 2025-03-26: one endpoint where clients POST messages and servers reply with JSON or an SSE stream.
U: You host a multi-user MCP server behind a load balancer.
T: Streamable HTTP replaced the older HTTP+SSE transport that used two endpoints.
F: Streamable HTTP requires a separate endpoint for every tool.
C: mcp.run(transport="streamable-http")
B: mcp.run(transport="____") ;; streamable-http ;; websocket ;; grpc ;; ftp

@ HTTP+SSE transport (legacy) | 7
D: The deprecated 2024-11-05 remote transport that used a separate SSE endpoint and a POST endpoint.
T: Servers can serve the legacy HTTP+SSE endpoints alongside Streamable HTTP for older clients.
F: HTTP+SSE is the newest MCP transport and replaced Streamable HTTP.

@ Server-Sent Events (SSE) | 7
D: A one-way HTTP streaming format (text/event-stream) a Streamable HTTP server can use to send several messages back.
U: A tool call sends progress updates before its final result over HTTP.
T: A server may answer a POST with an SSE stream that ends after the final response.
F: SSE streams let the client send requests to the server.

@ Mcp-Session-Id | 7
D: An HTTP header a Streamable HTTP server may assign in the initialize response, which the client then sends on every request.
U: A stateful remote server needs to recognise which session each POST belongs to.
