# Agentic AI. Lessons: 1 what is an agent, 2 reasoning patterns, 3 tools/MCP, 4 memory, 5 multi-agent patterns, 6 CrewAI, 7 OpenAI Agents SDK, 8 ADK/MAF/AutoGen, 9 smolagents/Pydantic AI/others, 10 A2A/eval/safety
@ AI agent | 1
D: A system where an LLM dynamically decides the control flow — choosing actions, observing results and continuing until a goal is met.
T: In an agent, the model decides which tool to call next.
F: An agent always follows a fixed sequence of hard-coded steps.
C: while not done:\n    resp = llm(messages, tools)\n    done = not resp.tool_calls

@ Workflow (vs agent) | 1
D: LLMs and tools orchestrated through predefined code paths rather than model-directed control flow.
U: The steps are known in advance: extract, validate, summarize.
T: Workflows are more predictable than agents.
F: Workflows let the LLM invent new steps at runtime.
C: summary = summarize(validate(extract(doc)))

@ Agent loop | 1
D: The repeated cycle of calling the model, executing requested tools and appending results until no more tool calls are requested.
T: The loop usually ends when the model replies without tool calls.
F: The agent loop ends after exactly one tool call.
C: for step in range(max_steps):\n    resp = llm(messages, tools)\n    if not resp.tool_calls:\n        break

@ Prompt chaining | 1
D: A workflow pattern where each LLM call processes the previous call's output.
T: Prompt chaining trades latency for accuracy by splitting a task into steps.
F: Prompt chaining requires multiple agents talking freely.
C: outline = llm(f"Outline: {topic}")\ndraft = llm(f"Write from outline: {outline}")

@ Orchestrator-workers | 1
D: A pattern where a central LLM breaks a task into subtasks, delegates them to workers and combines results.
T: The orchestrator decides the subtasks dynamically.
F: In orchestrator-workers, subtasks are fixed in advance.
C: subtasks = orchestrator(task)\nresults = [worker(s) for s in subtasks]

@ Evaluator-optimizer | 1
D: A pattern where one LLM generates and another evaluates and gives feedback in a loop.
U: Translations must be refined until a reviewer is satisfied.
T: Evaluator-optimizer loops until quality criteria are met.
F: Evaluator-optimizer runs the generator only once.
C: while not ok:\n    draft = gen(task, feedback)\n    ok, feedback = critic(draft)

@ Parallelization pattern | 1
D: Running LLM calls simultaneously, either sectioning a task or voting across several samples.
T: Voting runs the same prompt several times and aggregates answers.
F: Parallelization always slows down total latency.
C: answers = await asyncio.gather(*[llm(q) for _ in range(5)])

@ Agent guardrails | 1
D: Controls that validate inputs, outputs and actions to keep an agent safe and on task.
T: Guardrails can block a run before an unsafe action executes.
F: Guardrails are only used after the agent finishes.
C: if violates_policy(user_input):\n    raise Blocked()

@ ReAct | 2
D: Reason + Act: interleaving thoughts, tool actions and observations in a loop.
T: ReAct was proposed by Yao et al. in 2022.
F: ReAct never calls tools.
C: Thought: I need X\nAction: search("X")\nObservation: ...

@ Plan-and-execute | 2
D: A planner LLM writes a multi-step plan, an executor runs the steps, and a replanner updates the plan.
U: A long research task has a clear structure and you want fewer expensive model calls.
T: Plan-and-execute separates planning from execution.
F: Plan-and-execute cannot change the plan once it starts.
C: plan = planner(task)\nfor step in plan:\n    result = executor(step)\nplan = replanner(task, results)

@ ReWOO | 2
D: Reasoning WithOut Observation: plan all tool calls with variable placeholders, execute them, then solve.
T: ReWOO reduces LLM calls by planning tool use up front.
F: ReWOO calls the LLM after every single tool result.
C: # Plan: #E1 = search(...); #E2 = lookup(#E1); Solve with #E1, #E2

@ LLMCompiler | 2
D: Planning tool calls as a task DAG so independent calls run in parallel.
T: LLMCompiler executes independent tool calls concurrently.
F: LLMCompiler compiles Python into machine code.
C: # tasks with dependencies -> parallel execution

@ Reflection | 2
D: Having the model critique its own output and revise it.
T: Reflection loops can improve code and writing quality.
F: Reflection means retrieving documents from a vector store.
C: critique = llm(f"Critique this answer: {draft}")\nfinal = llm(f"Revise using: {critique}")

@ Reflexion | 2
D: An approach storing verbal feedback from failed attempts in memory to improve later attempts.
T: Reflexion uses self-generated feedback as memory.
F: Reflexion updates the model's weights with gradient descent.
C: memory.append(f"Last attempt failed because {reason}")

@ Self-consistency | 2
D: Sampling several reasoning paths and taking the majority answer.
T: Self-consistency trades extra compute for more reliable answers.
F: Self-consistency uses a single greedy decode.
C: answers = [llm(q, temperature=0.8) for _ in range(5)]\nfinal = Counter(answers).most_common(1)[0][0]

@ Tree of Thoughts | 2
D: Exploring multiple reasoning branches with evaluation and backtracking.
T: Tree of Thoughts can backtrack from unpromising branches.
F: Tree of Thoughts explores only one reasoning path.
C: # expand thoughts -> score -> prune -> expand best

@ LATS | 2
D: Language Agent Tree Search: Monte Carlo tree search over agent actions with LLM value estimates.
T: LATS combines tree search with LLM-based evaluation.
F: LATS is a vector index.
C: # select -> expand -> evaluate -> backpropagate

@ Function calling | 3
D: The model returns a structured request (tool name + JSON arguments) that your code executes.
T: The model never executes the tool itself; your application does.
F: Function calling lets the model run arbitrary code on the provider's servers by default.
C: {"name": "get_order_status", "arguments": {"order_id": "A17"}}

@ Tool schema | 3
D: The name, description and JSON Schema parameters that tell the model what a tool does and how to call it.
T: Clear, distinct tool descriptions improve tool selection.
F: Tool descriptions are ignored by the model.
C: {"name": "get_weather", "description": "Get weather for a city.", "parameters": {"type": "object", "properties": {"city": {"type": "string"}}}}

@ Idempotent tool | 3
D: A tool that produces the same effect if called repeatedly with the same arguments.
T: Idempotent tools are safer when agents retry.
F: Idempotent tools must change state every time they are called.
C: def set_status(ticket_id, status): ...   # same args -> same final state

@ Model Context Protocol | 3
D: An open protocol (introduced by Anthropic in 2024) connecting AI applications to tools, resources and prompts via servers.
U: You want one integration that works across many AI apps and IDEs.
T: MCP messages use JSON-RPC 2.0.
F: MCP is a vector database format.
C: from mcp.server.fastmcp import FastMCP\nmcp = FastMCP("weather")

@ MCP host | 3
D: The AI application (IDE, chat app, agent) that contains MCP clients.
T: A host can connect to several MCP servers through clients.
F: The host is the server that exposes tools.
C: # Claude Desktop / an IDE acting as the MCP host

@ MCP server | 3
D: A program that exposes tools, resources and prompts to MCP clients.
T: MCP servers can run locally over stdio or remotely over HTTP.
F: MCP servers can only expose prompts.
C: @mcp.tool()\ndef forecast(city: str) -> str: ...

@ MCP tools | 3
D: Model-invoked functions exposed by an MCP server.
T: Tools are the MCP primitive the model calls to take actions.
F: MCP tools are read-only documents.
C: @mcp.tool()\ndef search(query: str) -> str: ...

@ MCP resources | 3
D: Read-only data or context (files, records) exposed by an MCP server.
T: Resources provide context rather than actions.
F: Resources are functions that change external state.
C: @mcp.resource("docs://{name}")\ndef doc(name: str) -> str: ...

@ MCP prompts | 3
D: Reusable prompt templates exposed by an MCP server.
T: MCP servers can offer prompt templates to hosts.
F: MCP prompts are model weights.
C: @mcp.prompt()\ndef review(code: str) -> str:\n    return f"Review this code: {code}"

@ MCP sampling | 3
D: A client feature letting a server ask the host's LLM to generate a completion.
T: Sampling lets servers use the host's model without their own API key.
F: Sampling means the server picks random tools.
C: # server -> client: sampling/createMessage

@ MCP elicitation | 3
D: A client feature that lets a server request additional input from the user.
T: Elicitation lets servers ask users for missing information.
F: Elicitation deletes user data.
C: # server -> client: elicitation/create

@ stdio transport | 3
D: MCP transport that runs a local server as a subprocess communicating over standard input/output.
T: stdio is typical for local MCP servers.
F: stdio is used for remote servers across the internet.
C: {"command": "python", "args": ["server.py"], "transport": "stdio"}

@ Streamable HTTP transport | 3
D: MCP transport for remote servers over HTTP that replaced the older HTTP+SSE transport.
T: Streamable HTTP is the recommended transport for remote MCP servers.
F: Streamable HTTP only works on localhost.
C: {"url": "https://example.com/mcp", "transport": "streamable_http"}

@ Code execution sandbox | 3
D: An isolated environment (container, E2B, Modal, WebAssembly) for running agent-generated code.
U: Your agent writes Python to analyze uploaded CSVs.
T: Agent-generated code should never run unsandboxed on production hosts.
F: Agent-written code is always safe to run directly on your server.
C: sandbox.run_code(agent_code, timeout=30)

@ Short-term memory | 4
D: Working memory for the current conversation or task, such as message history and thread state.
T: Short-term memory is scoped to a thread or session.
F: Short-term memory persists across all users forever.
C: agent.invoke(msg, {"configurable": {"thread_id": "t1"}})

@ Long-term semantic memory | 4
D: Facts remembered across sessions, such as user preferences or company knowledge.
U: The assistant should remember a user prefers Python in every future chat.
T: Long-term memories are often stored in a database or vector store.
F: Long-term memory disappears when the thread ends.
C: store.put(("users", uid), "pref_lang", {"value": "python"})

@ Episodic memory | 4
D: Memory of past experiences or trajectories, often reused as few-shot examples.
T: Successful past trajectories can be retrieved as examples.
F: Episodic memory stores only the system prompt.
C: examples = memory.search(similar_to=task, kind="successful_runs")

@ Procedural memory | 4
D: Knowledge of how to act, such as rules in the system prompt or learned instructions.
T: Updating an agent's instructions based on feedback is a form of procedural memory.
F: Procedural memory stores raw chat logs only.
C: system_prompt += "\nAlways confirm before deleting files."

@ Conversation summarization | 4
D: Replacing older turns with a running summary to stay within the context window.
T: Summarization trades detail for a smaller context.
F: Summarization increases the number of tokens sent.
C: SummarizationMiddleware(model="openai:gpt-5.4-mini", trigger=("tokens", 4000))

@ Hot-path memory writing | 4
D: The agent itself decides during the conversation to save a memory, typically via a tool.
T: Hot-path writes make memories available immediately.
F: Hot-path writing happens only in an offline batch job.
C: @tool\ndef save_memory(fact: str) -> str: ...

@ Background memory writing | 4
D: A separate process extracts and stores memories after the conversation, without slowing replies.
T: Background extraction avoids adding latency to responses.
F: Background writing blocks the user's response.
C: # after the chat: extract facts -> upsert into the store

@ Letta | 4
D: A framework (formerly MemGPT) for stateful agents with self-editing persistent memory blocks.
T: Letta was previously known as MemGPT.
F: Letta is a vector database by Meta.
C: # Letta agent with core memory blocks the agent can edit

@ Mem0 | 4
D: A memory layer that extracts, stores and retrieves user memories for LLM apps.
T: Mem0 provides long-term memory as a service or library.
F: Mem0 is an LLM serving engine.
C: m.add("I prefer vegetarian food", user_id="u1")

@ Supervisor pattern | 5
D: A manager agent delegates to specialist agents and integrates their results.
U: A research manager coordinates a searcher, an analyst and a writer.
T: The supervisor decides which specialist acts next.
F: In the supervisor pattern, specialists never report back.
C: # supervisor -> [searcher | analyst | writer] -> supervisor

@ Hierarchical agents | 5
D: Supervisors of supervisors: teams of agents organized in levels.
T: Hierarchical systems scale to many agents by nesting teams.
F: Hierarchical agents must be flat.
C: # CEO agent -> team leads -> workers

@ Handoff / swarm | 5
D: Agents transfer control directly to each other without a central coordinator.
U: A triage agent should pass billing questions to a billing agent.
T: After a handoff, the receiving agent continues the conversation.
F: Handoffs require restarting the conversation from scratch.
C: triage = Agent(name="Triage", handoffs=[billing, tech])

@ Sequential pipeline of agents | 5
D: Agents run in a fixed order, each consuming the previous agent's output.
T: Draft → edit → fact-check is a sequential multi-agent pipeline.
F: Sequential pipelines run all agents at the same time.
C: crew = Crew(agents=[writer, editor], tasks=[draft, edit], process=Process.sequential)

@ Debate pattern | 5
D: Agents argue or critique each other's answers to improve accuracy.
T: A proposer and a critic can improve answers through debate.
F: Debate means the agents never see each other's answers.
C: for _ in range(3):\n    answer = proposer(q, critique)\n    critique = critic(answer)

@ Group chat | 5
D: Agents share one conversation and a selector picks the next speaker.
T: AutoGen popularized group chats with selector-based speaker choice.
F: Group chat forbids more than two agents.
C: SelectorGroupChat([planner, coder, reviewer], model_client=client)

@ Context isolation | 5
D: Giving each agent only the context it needs instead of the whole shared history.
T: Context isolation reduces confusion and token cost in multi-agent systems.
F: Every agent should always receive the entire conversation history.
C: worker_input = {"task": subtask}   # not the full transcript

@ Termination condition | 5
D: A rule that ends a multi-agent conversation, such as a max turn count or an approval message.
T: Without termination conditions, multi-agent chats can loop forever.
F: Termination conditions are only needed for single-agent systems.
C: MaxMessageTermination(10) | TextMentionTermination("APPROVED")

@ CrewAI | 6
D: A Python framework for role-based multi-agent crews and event-driven Flows, independent of LangChain.
T: CrewAI organizes work into agents, tasks and crews.
F: CrewAI is built on top of LangGraph.
C: from crewai import Agent, Task, Crew, Process

@ CrewAI Agent | 6
D: A CrewAI unit defined by role, goal, backstory, tools and an LLM.
T: role, goal and backstory shape how a CrewAI agent behaves.
F: CrewAI agents cannot use tools.
C: Agent(role="Senior Research Analyst", goal="Find developments in {topic}", backstory="Expert analyst.", tools=[SerperDevTool()])
B: researcher = Agent(\n    role="Analyst",\n    goal="Research {topic}",\n    ____="You cite sources carefully.",\n) ;; backstory ;; persona ;; history ;; context

@ CrewAI Task | 6
D: A unit of work with a description, an expected_output and an assigned agent.
T: expected_output describes what the task should produce.
F: Tasks in CrewAI have no description.
C: Task(description="Research {topic}", expected_output="10 bullet points", agent=researcher)
B: task = Task(description="Summarize the report", ____="A 5-bullet summary", agent=writer) ;; expected_output ;; output ;; result ;; goal

@ CrewAI Crew | 6
D: A team of agents and tasks executed according to a process.
T: crew.kickoff(inputs={...}) starts the crew and fills {placeholders}.
F: A crew can contain only one agent.
C: crew = Crew(agents=[a, b], tasks=[t1, t2], process=Process.sequential)\nresult = crew.kickoff(inputs={"topic": "Graph RAG"})
B: result = crew.____(inputs={"topic": "Graph RAG"}) ;; kickoff ;; run ;; start ;; invoke

@ Process.sequential | 6
D: CrewAI process where tasks run one after another in order.
T: In a sequential process, task outputs can feed later tasks.
F: Process.sequential runs all tasks in parallel.
C: Crew(..., process=Process.sequential)

@ Process.hierarchical | 6
D: CrewAI process where a manager LLM or agent delegates tasks and validates results.
U: You want a manager to decide which agent handles each part.
T: The hierarchical process requires a manager_llm or manager_agent.
F: The hierarchical process has no manager.
C: Crew(..., process=Process.hierarchical, manager_llm="openai/gpt-5.5")

@ Task context | 6
D: The context=[other_task] option that passes earlier task outputs into a task.
T: context=[research] gives the writing task the research output.
F: context deletes the outputs of previous tasks.
C: Task(description="Write article", expected_output="markdown", agent=writer, context=[research])

@ output_pydantic | 6
D: Task option that validates the task's output into a Pydantic model.
T: output_pydantic makes task output structured.
F: output_pydantic changes the agent's LLM.
C: Task(description="Extract", expected_output="JSON", agent=a, output_pydantic=Ticket)

@ CrewAI Flow | 6
D: Event-driven orchestration with typed state where methods are triggered by @start, @listen and @router.
U: You need deterministic control and state around autonomous crews.
T: Flows can call crews inside their steps.
F: Flows cannot hold state.
C: class BlogFlow(Flow[State]):\n    @start()\n    def pick(self): ...\n    @listen(pick)\n    def write(self): ...

@ @start | 6
D: Flow decorator marking an entry-point method.
T: @start methods run when the flow is kicked off.
F: @start methods run only after every other method finishes.
C: @start()\ndef pick_topic(self): ...

@ @listen | 6
D: Flow decorator that runs a method after another method (or route label) completes.
T: @listen(pick_topic) runs after pick_topic finishes.
F: @listen runs a method before its trigger.
C: @listen(pick_topic)\ndef write(self): ...

@ @router | 6
D: Flow decorator for a method that returns a label used to branch to listeners.
T: A @router returning "publish" triggers methods decorated with @listen("publish").
F: @router can only return booleans.
C: @router(write)\ndef check(self):\n    return "publish" if ok else "rewrite"

@ crewai CLI | 6
D: Command-line tool to scaffold and run CrewAI projects with YAML configs.
T: crewai create crew my_crew scaffolds agents.yaml and tasks.yaml.
F: The crewai CLI only works for JavaScript projects.
C: crewai create crew my_crew\ncrewai run

@ OpenAI Agents SDK | 7
D: OpenAI's lightweight, provider-agnostic agent framework with Agent, Runner, tools, handoffs, guardrails, sessions and tracing.
T: The Agents SDK is the production successor to the experimental Swarm project.
F: The Agents SDK only works with GPT models and cannot use other providers.
C: from agents import Agent, Runner\nresult = Runner.run_sync(agent, "Hello")

@ Runner | 7
D: The Agents SDK class that executes the agent loop via run, run_sync or run_streamed.
T: Runner.run_sync(agent, input) returns a result with final_output.
F: Runner defines the agent's instructions.
C: result = Runner.run_sync(triage, "What's my balance?")\nprint(result.final_output)
B: result = Runner.____(agent, "Hello")\nprint(result.final_output) ;; run_sync ;; kickoff ;; invoke ;; execute

@ function_tool | 7
D: Agents SDK decorator that turns a Python function into a tool with an auto-generated schema.
T: @function_tool uses the function signature and docstring to build the tool.
F: @function_tool requires writing JSON schemas manually.
C: @function_tool\ndef get_balance(account_id: str) -> str:\n    """Return the balance."""

@ Handoff (Agents SDK) | 7
D: Delegating the conversation to another agent, exposed to the model as a transfer tool.
T: Handoffs appear to the model as tools like transfer_to_billing.
F: After a handoff, the original agent keeps control of the conversation.
C: triage = Agent(name="Triage", instructions="Route users.", handoffs=[billing, tech])

@ Agents as tools | 7
D: Calling a sub-agent as a tool so the manager agent stays in control.
T: agent.as_tool(...) lets a manager use a sub-agent without handing off control.
F: Agents as tools permanently transfer the conversation.
C: manager = Agent(name="Manager", tools=[translator.as_tool(tool_name="translate", tool_description="Translate text")])

@ Input guardrail | 7
D: A check that runs on the user input alongside the agent and can trip a wire to stop the run.
U: Block requests that ask the support bot to do homework.
T: A triggered tripwire raises InputGuardrailTripwireTriggered.
F: Guardrail tripwires are silently ignored.
C: @input_guardrail\nasync def check(ctx, agent, inp):\n    return GuardrailFunctionOutput(output_info=None, tripwire_triggered=is_bad(inp))

@ output_type | 7
D: Agents SDK option that makes the agent's final output a structured type such as a Pydantic model.
T: output_type=MyModel makes final_output a validated object.
F: output_type selects the model provider.
C: Agent(name="Extractor", instructions="Extract", output_type=Invoice)

@ Sessions (Agents SDK) | 7
D: Automatic conversation memory across runs, e.g. SQLiteSession.
T: Passing the same session keeps prior turns.
F: Sessions in the Agents SDK store only images.
C: session = SQLiteSession("user-1")\nRunner.run_sync(agent, "Hi", session=session)

@ Built-in tracing | 7
D: The Agents SDK's automatic recording of agent runs, tool calls, handoffs and guardrails.
T: Tracing is enabled by default in the Agents SDK.
F: The Agents SDK has no tracing support.
C: with trace("support-workflow"):\n    Runner.run_sync(agent, "hi")
